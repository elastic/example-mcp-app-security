01Executive summary

A Tines→Elastic converter is not a translator. The two systems differ in execution model, not just syntax, so a meaningful share of real stories cannot be converted faithfully. The plan below treats that as the central design constraint rather than an edge case.

219
Tines formula functions to account for, across 13 categories
3
Custom Liquid filters in the Workflows engine: json_parse, entries, pick
0
Regex filters available — against 3 Tines regex functions in wide use
Recommendation — ship the common subset, report the rest Convert what converts, and emit an explicit fidelity report for what doesn't. The failure mode to avoid is YAML that validates but behaves differently — a silently wrong containment workflow is far worse than a loud refusal.
Liquid filter extensions are a separate PR Closing the regex/hashing/parsing gaps means touching create_workflow_liquid_engine.ts, a shared Kibana platform file. That is a platform change with its own blast radius and reviewers — it does not belong inside the converter PR.

02Source schema: Tines stories

There is no published JSON Schema. schema_version is an internal integer — observed 30 in a live export (2026-09-03), not the 18 this report first inferred from docs. The contract is the export endpoint GET /api/v1/stories/{id}/export plus the action docs.

{
  "schema_version": 30,
  "standard_lib_version": 94,
  "action_runtime_version": 87,
  "name": "Suspicious login triage",
  "guid": "8de58314250ff167127d6ae213711de9",
  "agents": [ /* the actions */ ],
  "links":  [ { "source": 0, "receiver": 7 } ],  // INDICES into agents[]
  "diagram_layout": "{\"<guid>\":[105,-195]}",        // stringified JSON
  "entry_agent_guid": null,
  "exit_agent_guids": [],
  "send_to_stories": [], "forms": [], "pages": [], "tags": [],
  "keep_events_for": 86400,
  "origin_story_identifier": "cloud:<tenant>:<story>"
}
Two traps worth flagging up front links[] references agents by array index, not guid — any reordering breaks the graph. And Agents::TriggerAgent is the Condition action, not a story trigger. Wire that wrong and every conditional in every converted story inverts.

Data manipulation is one action type with eight modes

There is no dedicated transform step. Everything is EventTransformationAgent with a mode discriminator.

modePurposeKey options
message_onlyThe workhorse. Emit an arbitrary payloadpayload, loop
explodeArray → N separate eventspath, to, limit (default 500)
extractRegex capture into named fieldsmatchers[{path,regexp,to}], emit_no_match
implodeReassemble a previous explodeitem_path, guid_path, size_path, seconds

Two details that shape the converter message_only has its own loop: point it at a list and the payload evaluates per element, exposing LOOP.value, .index, .key and — critically — .previous_result. That is a reduce. Separately, explode stamps a correlation guid + index + size into every child event, which is exactly what implode consumes to rejoin the fan-out.

Source of truth: src/platform/packages/shared/kbn-workflows/spec/schema.ts.

                  # kibana.request | elasticsearch.request | elasticsearch.esql.query
    if: "..."       # KQL condition, max 2000 chars
    with: { url: ..., method: GET }

    on-failure:
      retry: { max-attempts: 3, delay: 3s }

The entire data-manipulation surface is one step type

grep 'StepCategory.Data' across the whole spec returns exactly one hit: data.set. No map, filter, reduce, extract, or parse step exists. All shaping happens inside Liquid.

// kbn-workflows/spec/schema.ts:375
export const DataSetStepInputSchema = z
  .record(z.string(), z.unknown())
  .describe('Key-value pairs... Access via {{ variables.key_name }}');

export const DataSetStepSchema = BaseStepSchema.extend({
  type: z.literal('data.set'),
  with: DataSetStepInputSchema,
});
A schema constraint with real consequences data.set is BaseStepSchema.extend only — no .merge(StepWithForEachSchema), no .merge(StepWithOnFailureSchema). It accepts name/type/if/with and nothing else: no per-step foreach, no on-failure. A Tines transform inside an exploded scope needs its foreach hoisted a level up.

The Liquid engine is an allowlist

From kbn-workflows/common/utils/create_workflow_liquid_engine.ts:

Tags — 16 permitted

Everything else is deleted from the engine: an unknown tag is a parse error, not a passthrough.

assign · for · capture · case · comment · decrement · increment · cycle · if · unless · break · continue · raw · echo · liquid · #

Custom filters — all three of them

json_parseJSON string → object
entriesobject → [{key,value}]
pickkeep dotted paths, preserving nesting

Plus liquidjs built-ins. ownPropertyOnly: true, no filesystem, parseLimit 150k, renderLimit 1000ms, memoryLimit 15MB.

The render limit kills large loops regardless of translation quality Tines permits a 20,000-element loop with a 5-minute timeout. Workflows gives Liquid 1000ms and 15MB per render. Even where LOOP.previous_result or REDUCE can be faked with assign inside {% for %}, a large Tines loop will not survive the translation.

04The three structural mismatches

Mismatch 1 — DAG vs tree

TinesElastic Workflows
Structureflat agents[] + links[] edgesordered, nested steps[] tree
Control flowimplicit, via edgesexplicit if/switch/foreach
Reconvergencenative — N in-edges allowedno direct representation

Any node with multiple in-edges — a join — has no clean tree home. In the sample story inspected, one node fans out to three receivers and two paths reconverge. Common case, not edge case.

Mismatch 2 — per-event fan-out

Tines actions run once per event; an explode makes every descendant re-run per element, implicitly and transitively. Elastic runs each step once unless wrapped in foreach.

explode→ enrich→ condition→ notify   last three re-run per element, automatically

So explode must become a foreach that swallows its entire downstream subgraph — which couples the graph→tree pass to the explode pass.

Mismatch 3 — expression language

TinesElastic Workflows
Interpolation<<path.to.field>>{{ steps.x.output.y }}
FormulasUPCASE(user.job){{ user.job | upcase }}
Functions219 unique, 13 categories3 custom + liquidjs built-ins
RegexREGEX_EXTRACT, REGEX_REPLACE, MATCHnone
Referencesslugs (My action→my_action)steps.<name>.output

The good news The most common archetype — webhook → HTTP enrich → condition → notify — maps cleanly end to end. That is the MVP target, and it covers a meaningful share of real stories.

Escape hatches for the gaps

  • Regex (REGEX_EXTRACT, extract mode) → elasticsearch.esql.query with GROK/DISSECT, or Painless via elasticsearch.request
  • Aggregation (GROUP_BY, TALLY) → ES|QL STATS
  • Parsing (CSV_PARSE, XML_PARSE) → ingest pipeline, or a new Liquid filter (separate PR)
  • Hashing / signing → no in-engine option; needs a platform filter or an external connector

07Design decisions

D1 — Graph → tree via dominator analysis, hoist-and-gate for joins

Compute a topological order, then the dominator tree. A node nests under its immediate dominator. Join nodes (multiple in-edges) are hoisted to the dominator's level and gated with an if.

Why not subtree duplication The obvious alternative — copy the subtree down each inbound path — produces exponential YAML on diamond stories and, far worse, duplicates side effects. An HTTP POST reachable by two paths would fire twice. Verbose is survivable; silently doubling a containment action is not.

Cycles: Tines permits them. Workflows has while but no arbitrary back-edge. Detected cycles are classified (D10): polling-pattern cycles — the dominant shape, 8 in 7 of 14 real elastic/infosec stories — convert to a while step; irreducible cycles are reported unconvertible, never approximated.

D2 — Explode scope is computed with the tree, not after it

You cannot compute nesting without knowing explode scopes, and you cannot compute explode scopes without the dominator tree. Hence one pass, not two.

D3 — The capability matrix is data, and every row is a test

The emitter is a lookup over capability-matrix.ts; it contains no per-function logic. Non-negotiable rule: a converted verdict requires a passing test proving the emitted Liquid matches Tines' output for at least one input. Rows without tests default to unconvertible. An untested “converted” claim is the single most dangerous failure mode this tool has.

D4 — Microcks (Testcontainers) as the only connector stub engine

No public Tines OpenAPI spec exists — verified, Tines publishes none. So we author OpenAPI 3.1 specs for the external APIs the fixture stories touch. Those specs are the durable asset and are mock-engine agnostic.

Correction. An earlier draft rejected Microcks as “Kubernetes-native and disproportionate.” That was wrong. @microcks/microcks-testcontainers (Apache-2.0, CNCF incubating) boots a throwaway microcks-uber container from a single call — no Kubernetes, no standing server. Microcks is the sole stub engine; a later draft's Prism fallback was also dropped.
CapabilityWhat it buys this project
getServiceInvocationsCountCall-equivalence assertions
Content-based dispatchersDriving both branches of a converted if

None of these are offered by a spec-replay mock (Prism, WireMock static stubs).

Why those matter concretely. (1) Invocation counting is how we prove the converted workflow made the same calls as the story — without it we assert on our own client's logs, marking our own homework. (2) Content-based dispatch is required to drive both branches of a converted if. (3) Stateful mocks are the only honest way to test a converted explode → per-item HTTP → implode chain where call N+1 depends on call N.

Cost is one Docker dependency, already being paid by the in-flight e2e-mcp-app-test-harness-with-local-docker-es change. No fallback engine and no StubEngine abstraction — Docker is a given in this project's environments, so a seam whose second implementation must throw NotSupported for the assertions that matter buys nothing. Phases 0–3 are pure functions over JSON needing no HTTP, so the containerised suite starts at Phase 6; if Docker is absent it fails loudly rather than degrading to a weaker green.

08Implementation plan

Eight phases, 75 tasks, landing in elastic/example-mcp-app-security on feat/tines-story-converter as an OpenSpec change. Phases 0–6 are headless and independently testable; the MCP surface comes last, on top of a proven core.

Phases

PHASE 0 · 8 tasks

Schema foundation

zod schemas for the export envelope and all 8 agent types. Parse real story exports; fail loudly on unknown type rather than silently skipping.

PHASE 1 · 10 tasks

Formula lexer + parser

<<...>> extraction, function-call AST, slug resolution with Tines' documented sluggification and collision rules.

PHASE 2 · 6 tasks

Capability matrix + emitter

All 219 rows as data. Emitter is a pure lookup — no per-function branching. Unknown function ⇒ unconvertible, never a guess.

PHASE 3 · 10 tasks

Graph → tree

Topological sort, dominator tree, join hoisting, explode-scope resolution, cycle classification (D10). The hardest phase; property-based tests over generated DAGs.

PHASE 4 · 11 tasks

YAML emit + fidelity report

Inline # TINES-UNCONVERTIBLE: comments at the exact step, plus fidelity.json. Every output validated against the live WorkflowSchema zod parse.

PHASE 5 · 7 tasks

Golden fixtures

Real story exports → expected YAML. Diffed on every run. This is the agreed starting verification bar.

PHASE 6 · 12 tasks

Round-trip harness

Author OpenAPI 3.1 specs for external APIs, stub with Microcks (Testcontainers), execute the converted workflow, diff the observed request sequence against the Tines-run baseline.

PHASE 7 · 8 tasks

MCP tool + App UI

convert_tines_story tool plus a React view rendering the fidelity report — side-by-side story graph and emitted workflow, gaps highlighted.

Why the MCP surface lands last Phases 0–6 are headless and independently testable. Building UI on an unproven converter would mean debugging graph-nesting bugs through a chat client. The core earns its correctness first.

Validation against the elastic/infosec corpus

On 2026-09-03 the plan was tested against the elastic/infosec corpus — Elastic's own Tines estate: 14 top-level stories, 360 agents, 7 embedded sub-stories, schema_version 3 era (2021). Sanitized (options.secret redacted) and vendored as golden fixtures. Everything below is measured, not inferred.

The headline. Two assumptions did not survive. First, fan-in joins are the norm: 16 of 21 story graphs contain them, max indegree 7 (Implode Analysis in spam-analysis, fed by seven parallel enrichment branches). Second, cycles are common: 8 cycles across 7 of 14 stories — all async-API polling loops (see D10). The design's "cycles are rare, report unconvertible" stance would have hard-failed half this corpus.

Enough to falsify repeatedly; the capability matrix remains triage until the converter runs.

Corpus correction: cycles → while (D10)

The sanitized elastic/infosec corpus — 14 stories, 360 agents, 7 embedded sub-stories, vendored as golden fixtures — falsified the design’s “cycles are rare, report unconvertible” stance.

Falsified by corpus. 8 cycles in 7 of 14 real stories. Every one is the same shape: async API polling — poll HTTP → exit condition → bounded counter (“Counter < 20”) → delay → back-edge. Reporting them unconvertible would hard-fail half of Elastic’s own production Tines estate.

The target exists and fits: WhileStepSchema (kbn-workflows/spec/schema.ts) is a do-while step with {{ while.iteration }}, max-iterations, iteration-timeout, iteration-on-failure.

Tines polling cycleElastic whileRule
cycle body nodeswhile.stepsdirect
exit TriggerAgent ruleconditionnegated (do-while: loop while incomplete)
counter bound “< N”max-iterations: Nfrom the counter, never the 2000 default
delay nodeiteration-timeout / leading waitpreserve first-iteration delay

Classifier contract. A cycle converts only when: exactly one back-edge; the back-edge source is a delay or condition node; a TriggerAgent on the cycle supplies the exit condition; counter logic reduces to a numeric bound. Everything else is irreducible → unconvertible. All 8 vendored cycles are golden test cases.

Verdict: degraded until proven. Tines cycles re-emit events per iteration; while iterations share Liquid scope. A Microcks per-iteration emitted-event equivalence test must pass before any cycle is marked converted.

Resolved decisions

AI steps — corrected. An earlier draft of this report claimed the Tines AI Agent action “has no Workflows analogue.” That was wrong. Elastic Workflows ships a full AI step family: ai.agent (invoke an Agent Builder agent), ai.prompt, ai.classify and ai.summarize. The Tines AI Agent action is therefore in scope and maps natively to ai.agent, with ai.prompt as the simpler target for single-shot prompts.

Verified in agent_builder/common/step_types/run_agent_step.ts (RunAgentStepTypeId = 'ai.agent', StepCategory.Ai). Note the shape trap: agent-id, connector-id, inference-id and create-conversation are top-level kebab-case step fields, not nested under with. Only message, schema, attachments, conversation_id and configuration_overrides live inside with.

- name: triage
  type: ai.agent
  agent-id: "my-custom-agent"
  connector-id: "my-openai"
  create-conversation: true
  with:
    message: "Triage this alert: {{ steps.fetch_alert.output.body | json }}"
    schema:
      type: object
      properties:
        verdict: { type: string, enum: [true_positive, false_positive] }

Two caveats that keep this degraded rather than converted: a Tines AI action's tool bindings reference Tines tools, which have no automatic Agent Builder equivalent — the converter emits the prompt and flags tool bindings for manual mapping; and ai.agent requires a pre-existing agent-id, so the emitted step is a reference to an agent a human must create, not a self-contained translation.

Conversion score — yes, with a guard. The fidelity report emits a numeric score. The stated risk (a number that invites inflating the matrix) is real, so the score is defined to make gaming it visible rather than trusting discipline.
RuleWhy
Score = converted / total constructs. degraded counts as 0, never as partial credit. No fractional weighting to tune. A generous re-label moves the number the wrong way.
Report carries scoreBasis: matrix version, count per verdict, and the commit SHA of the matrix. A score is only comparable against the same matrix. Silent re-labelling changes the basis, which is visible in a diff.
A construct may only be converted if a passing equivalence test names it. Phase 2 gate. Untested constructs default to unconvertible, so the score cannot rise without a test.
CI fails if the score rises while the equivalence test count does not. Directly detects the failure mode: inflating the number by relaxing the matrix instead of adding capability.

An accurate low score is the desired output. If real stories convert at 40%, the report says 40% — that is a finding about scope, not a defect to tune away.
